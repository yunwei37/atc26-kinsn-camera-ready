Author Response

We thank the reviewers and the meta-reviewer for their careful reading and constructive feedback. The central clarification is the guarantee boundary: BPF-Ext preserves the existing verifier analysis by rechecking vanilla-eBPF proof code, while making the additional semantic-correctness obligation narrow and explicit. Kinsn structures this obligation as local Lean refinements; it does not claim whole-system verification.

### 1. Guarantee boundary and TCB (Meta, C, D, E)

BPF-Ext separates verifier analysis from semantic transparency. Before verification, the kernel expands each extended operation into vanilla eBPF and re-runs the existing verifier while validating proof-region control flow. An incorrect recognizer cannot make unsafe proof code bypass this analysis, but can change program semantics through an incorrect pattern, payload, operand mapping, or precondition. These recognizer-to-theorem obligations belong to Kinsn's semantic boundary; the verifier still establishes safety for the lowered program.

The native-emit boundary is a deliberate performance/trust tradeoff. Falling back to the verified proof sequence avoids an operation-specific native translation but also loses the hardware idiom; obtaining the speedup requires the JIT to emit the shorter architecture-specific sequence. Kinsn validates the intended translation offline by separately proving that the modeled eBPF expansion and an operand-parameterized native template refine the same specification. The residual implementation mappings are that the proof-sequence routine produces the modeled eBPF expansion, the recognizer and payload establish the theorem inputs and preconditions, and the handwritten emitter's bytes decode to the modeled native template. Thus, on the native-emitter side, the trusted step is faithful C instantiation of a semantically verified template, not an unverified semantic translation. The offline assurance base also includes Lean's checker, the semantic definitions and their ISA correspondence, and the theorem's observation relation.

We agree that loaded module C enlarges the kernel attack surface. The review's nearly 10K-LOC figure is nevertheless not 10K lines of native emitters: §6.3 reports the architecture-specific module trees, including shared headers, registration and proof-sequence code, test-only modules, and operations beyond Kinsn's seven. We did not separately measure emitter-only LOC and therefore do not claim an unsupported smaller number. The runtime TCB includes the existing verifier/JIT, the 929-line generic kernel path in Table 4, and loaded module code; the narrower operation-specific semantic obligation is the native emitter's correspondence above. BPF-Ext cannot require arbitrary third-party modules to provide this evidence, so deployment must restrict modules through the kernel's existing trust and review policy.

### 2. Lean semantics and proof maintenance (Meta, C, D-Q1)

The supplied development models the standard ALU64 operations needed by the demonstrated `extract` proof; RFC 9669 and Linux documentation are the normative references, but correspondence of this abstraction to legal eBPF encodings remains explicit in the assurance base. The ARM64 model is adapted from LNSym, cited as Ref. [1]. An eBPF-side lemma proves that the proof sequence refines a hardware-independent specification, and a native-side lemma proves that the native template refines the same specification; these lemmas are the correctness arguments for the two modeled translations. Recent Sail work, *Formal Specification of Linux eBPF Instruction Set Architecture in Sail* (eBPF '26), provides a broader formalization of sequential Linux eBPF instructions and is a promising common reference, but the current Lean model does not inherit its guarantees. The supplied archive illustrates this factoring for `extract`/ARM64 and should not be presented as the complete seven-operation/two-ISA proof set.

The intermediate specification also reduces proof coupling. If an operation has `m` legal eBPF patterns and `n` native templates with compatible preconditions and observations, direct pairwise checking needs up to `m*n` lemmas, whereas the shared specification needs `m+n` local refinement lemmas. This is a reduction in proof obligations, not a measured reduction in person-time. AI-assisted proof construction handled routine proof-search and script work; for completed, axiom-free proofs, this assistance is outside the logical TCB because Lean checks the resulting terms. The durable human maintenance and review burden remains the semantic definitions, legal encodings, specifications and preconditions, observations, and implementation mappings. We do not give an unsupported retrospective proof-LOC or person-time figure.

### 3. BPF-Ext versus Kinsn (C)

BPF-Ext is the reusable kernel mechanism: it defines how an extended operation carries verifier-visible proof code and a JIT-visible native implementation, and how the kernel verifies and emits it. Kinsn is one client, supplying seven hardware-idiom operations. §§7.1-7.3 evaluate Kinsn, while §7.4 uses whole-program native replacement to explore the broader BPF-Ext design space. We will reorganize §§4-5 around this end-to-end pipeline before introducing Kinsn examples and define family-selection policy before §7.

### 4. Gains, remaining gap, and ARM64 policy (C, D-Q2, E)

The 27 Kinsn-bearing microbenchmarks isolate sequences Kinsn can change and show 1.242x and 1.222x geometric-mean speedups on x86-64 and ARM64. §7.1 associates x86-64 gains with reduced code size and dynamic instruction overhead, and ARM64 gains with target-specific rotate/extract and load-fusion idioms. End-to-end applications also spend time in helpers, maps, tail calls, and other work outside Kinsn's instruction-selection scope, which dilutes application-level gains. The upper-bound experiment does not decompose the residual gap quantitatively: Cilium's 1.074x gain recovers 5.4% of the 2.358x whole-native gap while avoiding trust in whole native replacements.

Figure 6 shows that raw match coverage is not profitability: a family should be enabled only when it reduces dynamic work on the hot path enough to outweigh replacement cost. On ARM64 Katran, enabling all families applies 62 sites but yields 0.995x throughput; the conservative policy disables `bulk_memory`, `endian_fusion`, and `prefetch`, leaving 20 rotates and one extract and yielding 1.073x. This supports descriptor-family gating or lightweight cost guidance; a general automated cost model remains outside the submitted scope.

### 5. Microbenchmark provenance (E)

The evaluation uses the submitted 27 Kinsn-bearing microbenchmarks plus Cilium and Katran; the two baseline-only microbenchmarks are excluded from the geomean. The microbenchmarks are controlled kernels adapted from or modeled on real eBPF code shapes, not all verbatim extractions.
